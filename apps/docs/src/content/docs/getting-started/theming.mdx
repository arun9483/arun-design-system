Everything visual resolves through a four-tier chain of CSS custom properties. Components read
the top of the chain and know nothing about what is beneath.

```
primitives      --space-sm, --radius-full, --duration-fast     brand-independent
brand palette   --color-brand-700: #4338ca                     per brand
semantic        --color-text-accent: var(--color-brand-700)     per brand, per theme
component       --btn-bg: var(--color-text-accent)              per component
```

So a single rule in `btn.css` —

```css
.btn-primary {
  background-color: var(--btn-bg);
}
```

— produces a different colour in dark mode, and a different colour again under another brand,
without that rule or `Button.tsx` changing at all.

## Light, dark and system

Themes live on `:root`. Set `data-theme` on `<html>`:

| Mode   | How                                                |
| ------ | -------------------------------------------------- |
| system | default — follows `prefers-color-scheme`           |
| dark   | `document.documentElement.dataset.theme = 'dark'`  |
| light  | `document.documentElement.dataset.theme = 'light'` |

<Aside title="Why :root and not a wrapper">
Custom properties inherit through the DOM tree, and React portals move nodes out of it. A
popup portaled into `<body>` would not inherit tokens scoped to a wrapper element. Declaring
at `:root` means portaled content inherits correctly with no extra machinery.
</Aside>

## Custom brands

`createBrand()` generates a full palette and semantic layer from one seed colour, at build time:

```ts
// scripts/generate-brand.mjs
import { writeFile } from 'node:fs/promises';
import { createBrand } from '@arun-dev/tokens/createBrand';

await writeFile('src/brand.css', createBrand({ name: 'acme', seed: '#0ea5e9' }));
```

Then import `src/brand.css` in place of `@arun-dev/tokens/brands/default`. It emits the light,
dark and system variants together, so theming keeps working.

You can also pass a full palette instead of a seed if you already have one:

```ts
createBrand({ name: 'acme', palette: { 50: '#…', 100: '#…', /* … */ 950: '#…' } });
```

:::note[This site is that consumer]
Everything you see here renders in a brand generated exactly this way — one
`createBrand()` call from the seed `#7c3aed`, written to a file, imported in place of
`@arun-dev/tokens/brands/default`. See `apps/docs/scripts/generate-brand.mjs`.

So the component examples are **not** the default indigo brand. That is the point: no
component knows a brand exists, and swapping the token layer is the only change needed.
:::

## One brand per document

Brand and theme tokens are declared at `:root`, never scoped to a subtree, so a document
has exactly one brand. Rendering two brands on one page is deliberately not supported —
custom properties inherit through the DOM tree, and a React portal moves nodes out of it,
so a popup portaled into `<body>` would not inherit tokens scoped to a wrapper element.

To show a different brand, load a different brand stylesheet.

## Restyling one component

Override at the tier that matches the blast radius you want:

```css
:root {
  --color-text-accent: #7c3aed; /* every accent surface in the system */
  --chip-accent-bg: #f5f3ff; /* only accent chips */
}
```
